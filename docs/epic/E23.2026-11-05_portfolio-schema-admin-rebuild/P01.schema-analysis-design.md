# P01: schema-analysis-design

## 목표
- 현재 테이블, 엔티티, 연관 관계, 기존 SQL 파일의 현황과 문제점이 문서 하나로 정리되어 있다.
- 포트폴리오 콘텐츠 전체의 새 스키마 설계가 사용자 승인을 받은 상태로 문서화되어 있다. 설계에는 사이트별 노출 모델, 다국어 포함 여부, 기존 데이터 이관 방식, 호환성을 지키는 변경 순서, 롤백 조건이 들어 있다.
- 이후 Phase(마이그레이션 구현, Admin API 계약)를 만들 수 있을 만큼 범위가 나뉘어 있다.

## 구현 상세
- 접근: 읽기 전용 현황 분석 → `creative-design-brainstorm`으로 도메인 경계와 노출 모델 합의 → `database-schema-design` 규칙으로 DDL 설계 문서 작성 → 승인.
- 변경 범위: 문서만 작성하고 코드와 DB는 변경하지 않는다.
  - `database/design/`에 현황 분석 문서와 스키마 설계 문서 추가
  - 이 에픽 Readme의 Phase 목록과 `## 후속` 갱신
- 확인할 항목: Admin 인증 방식(`AdminAuthInterceptor`), DB 변경 관리 방식(수동 SQL 대 마이그레이션 도구), 운영 DB 기준선, 백로그 항목 중 이 에픽 범위와 겹치는 것.

## 체크리스트
- [ ] 테이블 목록, 엔티티, 연관 관계, 현재 문제점이 현황 분석 문서에 정리되어 있다.
- [ ] Admin 인증 방식과 DB 변경 관리 방식이 문서에 사실로 기록되어 있다.
- [ ] 도메인 경계(프로젝트, 경력, 교육, 자격증, 아티클, 기술 스택, 프로필, 미디어)가 설계 문서에 정의되어 있다.
- [ ] 사이트별 노출 모델이 설계 문서에 정의되어 있다.
- [ ] 프로필 i18n을 DB 범위에 넣을지 여부가 결정되어 문서에 기록되어 있다.
- [ ] 기존 데이터 이관 방식, 변경 순서, 롤백 조건이 설계 문서에 기록되어 있다.
- [ ] 사용자가 설계 문서를 승인했다.
- [ ] 후속 Phase 후보가 Readme `## 후속`에 범위와 함께 반영되어 있다.
