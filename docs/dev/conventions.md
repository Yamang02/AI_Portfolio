# Development Conventions

> Kind: conventions
> Status: maintained
> Scope: cross-stack

이 문서는 AI_Portfolio에서 공통으로 적용할 **코딩·협업 관례**를 정의한다. 개별 프레임워크, 배포, 보안, 데이터 모델의 상세 계약을 반복하지 않는다.

## 적용 원칙

- 정확성·가독성·예측 가능성을 형식적 규칙 준수보다 우선한다.
- 기존 공개 API, 도메인 불변식, 사용처 및 외부 계약을 확인한 뒤 변경한다.
- 단순성을 해치는 추상화나 미래를 가정한 범용화는 도입하지 않는다. 추상화가 필요하면 책임과 사용처를 설명한다.
- 기존 코드와 합의된 프로젝트 관례를 우선하고, 레거시 관례가 명백히 문제라면 근거와 변경 범위를 기록한다.

## 책임과 의존성

- 하나의 모듈·함수는 명확한 책임을 가진다. 복수 책임을 동시에 변경한다면 경계를 검토한다.
- 도메인 규칙과 외부 기술·입출력 세부사항은 가능한 한 분리한다.
- 백엔드의 Hexagonal Architecture 및 프론트엔드의 FSD 경계는 실제 코드와 [기존 기술 문서](../technical/README.md)에서 확인한다. 모든 도메인에 고정 파일 템플릿이나 BaseCrudService를 강제하지 않는다.
- 새로운 공통 계층·인터페이스·래퍼를 만들기 전에 기존 소유자와 공개 계약을 확인한다.
- API 응답·오류·영속성 계약은 기존 소비자와 마이그레이션 필요성을 함께 검토한다.

## 로직과 제어 흐름

- 로직은 검증 → 계산·변환 → 반환의 자연스러운 흐름을 우선한다.
- 예외 조건은 적절히 조기 반환해 불필요한 중첩을 줄인다.
- 복잡도가 이해를 방해하면 조건·계산·상태 전환을 이름 있는 함수로 분리한다. 중첩 깊이, 분기 수, 줄 수에 획일적 한도를 강제하지 않는다.
- 순수 계산에서는 외부 의존을 명시적 인자나 추상화로 전달해 예측·테스트 가능성을 높인다. I/O를 담당하는 함수까지 순수 함수로 제한하지 않는다.
- 컬렉션 처리는 의도가 명확한 루프, map/filter 등 언어 관용구 가운데 더 읽기 쉬운 방식을 선택한다. 특정 문법을 일괄적으로 금지하지 않는다.

## 이름과 상태

- 변수·함수·타입 이름은 현재의 의미와 책임을 정확하게 나타낸다.
- 하나의 변수를 서로 다른 의미로 재사용하지 않는다.
- 재할당이 불필요하면 `const`/`final` 등 불변 바인딩을 우선한다. 같은 의미의 단계별 정제가 더 분명할 때는 제한적으로 재할당할 수 있다.
- 입력, 정규화, 계산 결과처럼 서로 다른 의미의 상태는 구분한다.
- 특정 축약어·이름을 절대 금지하기보다 주변 문맥과 코드베이스의 표기 관례를 따른다.

## 오류·보안·데이터

- 오류는 발생한 계층의 책임에 맞춰 처리하고, 외부로 노출할 메시지와 내부 진단 정보를 구분한다.
- 외부 입력은 실제 신뢰 경계에서 검증한다. 타입 시스템만으로 런타임 입력 검증을 대신하지 않는다.
- 영속성 변경에서는 기존 데이터를 보존하고 호환성, 되돌리기, 검증 경로를 명시한다.
- 인증·권한·비밀값·외부 API·캐시 경계의 상세 규칙은 각각의 실제 구현과 주제별 기술 문서에서 확인한다. 오래된 문서의 구현 예시를 자동으로 현행 계약으로 간주하지 않는다.

## 변경·검증

- 가능한 한 하나의 변경에 하나의 의도를 둔다. 리팩터링과 기능 변경을 분리한다.
- 결함을 수정할 때는 재현 및 원인 근거를 먼저 확보한다.
- 변경한 계약에 맞춰 검증을 선택하고 실제 실행 결과만 보고한다.
- 테스트·빌드·브라우저 관찰은 서로 다른 증거이다. 실행 기준은 [development.md](./development.md)를 따른다.

## 구형 문서에서 유지·조정한 내용

이 문서는 `docs/basis/coding/CC-01-logic-level-rules.md`의 흐름·이름·순수 로직·불변 바인딩 원칙과 구형 에이전트 개발 가이드의 의존성 경계 원칙을 통합한 것이다.

원본의 **중첩 1단계, 상태 변화 5회, 분기 3개, 논리 연산자 2개, 명령형 루프 우선** 같은 수치·스타일 규칙은 보편적 강제 규칙으로 승격하지 않았다. 해당 숫자는 lint 규칙이나 팀 결정으로 별도 채택한 경우에만 강제한다. 구형 가이드의 특정 CRUD 파일 구조·구현 현황도 현재 규약이 아니다.

프론트엔드 및 백엔드의 세부 설계는 기존 주제별 문서와 실제 구현을 확인한 후 별도의 Dev authority로 이관한다.
